The main executable — explained, visually

The entry point: wsgi.py

Everything the server does starts here. It is imported by WSGI servers and the Flask CLI (which both look for a module-level app), and it can also be run directly as a script for local dev. Seven lines, three jobs.

Import the app factory Pulls create_app() out of the opencode package (in src/). The factory pattern keeps the import side-effect free — nothing runs until the app is actually built.

Build the Flask app at import time Creates the app, points it at the templates/ & static/ folders (explicit paths are needed because of the src/ layout), and registers the main blueprint. The module-level name app is the contract WSGI servers and the CLI look for.

7
Dev server, debug on app.run(debug=True) launches Werkzeug's dev server on 127.0.0.1:5000 with the interactive debugger and auto-reload. Fine for development — never for production (a debugger on a public port is a remote code-execution hole).

Two ways the executable starts

The same file, two personalities. The README's recommended dev command goes through the Flask CLI; the python wsgi.py path is the "direct script" fallback.

Path A — Flask CLI (documented dev command)

uv run flask --app wsgi run --debug — the CLI imports wsgi, finds the app object, and runs it. The --debug flag maps to the same debug=True behavior as line 7, plus the reloader.

Path B — Direct script dev only

python wsgi.py executes line 7 and calls app.run(debug=True). Identical result on localhost; it's just the "run this file" mental model instead of a CLI discovery mechanism.

Path C — A real WSGI server (production)

Tools like gunicorn or uwsgi would run wsgi:app — import the module, grab the app object, and serve it behind the production-grade server (no debugger, no reloader). Nothing in the file needs to change: that's the whole point of the factory + module-level app convention.

How WSGI servers find it
The "WSGI" in the filename stands for Web Server Gateway Interface — the Python standard for how servers talk to web apps. The file's real contract is just: "expose a callable named app". Everything else (blueprints, templates, static files) hangs off that callable.

What the browser actually loads

The rendered HTML is a thin shell. The page pulls two more resources, and all game logic lives in main.js — the server never sees the game:

1. css/main.css — dark neon theme, HUD, layout (~315 lines).
2. js/main.js — the entire game engine: physics, levels, enemies, audio synth, render loop (~1,412 lines).
3. After that, the connection goes quiet: the game runs entirely client-side with requestAnimationFrame, and persistence uses localStorage, not the server.

Why so little Python?
This is a deliberate architecture: Flask serves one static-ish page (built by Jinja), and the real product — a playable game — is 99% browser JavaScript. The backend is a glorified static file server with templating.

src/opencode/__init__.pyapp factory
from pathlib import Path

from flask import Flask

from .routes import main_bp


def create_app() -> Flask:
    app = Flask(
        __name__,
        template_folder=str(Path(__file__).parent / "templates"),
        static_folder=str(Path(__file__).parent / "static"),
    )
    app.register_blueprint(main_bp)
    return app

The template_folder / static_folder paths are computed from __file__ — this is what makes the src/ layout work no matter where the package is imported from.

src/opencode/routes.pyblueprint
from flask import Blueprint, render_template

main_bp = Blueprint("main", __name__)


@main_bp.route("/")
def index():

The other "executable": the game engine

The real brain of the project. main.js is a 1,412-line IIFE that runs the whole game with zero frameworks and zero assets — physics, AI, sound synth, and rendering are all hand-rolled. Watch the heartbeat cycle below, then explore the game's states.

Every frame (~60×/s), the loop computes a clamped delta-time, updates state only while playing, and redraws. This is the classic game-loop pattern:

Levels as data

Levels aren't art assets — they're arrays of coordinates built by plain functions. Level 2's gauntlet, for example:

Three enemy types: walkers patrol between min/max, flyers (volts) bob sinusoidally, and shooters (turrets) aim at the player and lob plasma bolts. Physics constants: GRAV=2300, MOVE=340, JUMP_V=800 — plus coyote time (0.09 s) and jump buffering (0.12 s) so jumps feel forgiving.

Findings & gotchas

Real observations from reading the code — worth knowing before you touch anything.

⚠ Broken console script
pyproject.toml declares [project.scripts] opencode = "opencode:main", but src/opencode/__init__.py only defines create_app — no main function exists. Installing the package creates an opencode command that crashes on launch. The working entry is wsgi.py (via flask --app wsgi run).
⚠ README understates the game
The README says main.js is "~550 lines of canvas JavaScript". It's actually 1,412 lines — nearly 3×. The file has grown with Level 2 (turrets, flyers, keys/gates, projectiles).
ℹ src-layout needs PYTHONPATH
The package lives in src/ and isn't necessarily installed into the venv, so the README suggests PYTHONPATH=src uv run flask --app wsgi run as a fallback. uv sync normally installs the local package, making this unnecessary.
ℹ Debug mode = dev only
app.run(debug=True) (line 7) enables the Werkzeug debugger — handy locally, dangerous if ever exposed publicly. Production should import wsgi:app behind gunicorn/uWSGI instead.
ℹ Everything is client-side
After the initial page load there is no backend interaction at all — no APIs, no POST routes, no database. Persistence (best score, sound preference) is localStorage in the browser. The Python layer is 45 lines total; the game is 1,412.
